## งานเพิ่มเติมจากข้อกำหนด Final Project: API Readiness

Sprint 1 เดิมยังไม่ได้เชื่อม API; เพื่อให้ Sprint ถัดไปทำงานต่อได้ กำหนด API ที่ใช้เป็น **self-made local Coffee POS API** (ไม่ใช้ API ภายนอกหรือ API key) และกำหนดสัญญาไว้ดังนี้:

- `GET /api/menu` อ่านเมนู
- `GET /api/orders` อ่านออเดอร์ที่บันทึกแล้ว
- `POST /api/orders` ส่งรายการสินค้าและข้อมูลชำระเงินเพื่อสร้างออเดอร์
- DoD: JSON request/response, input validation, HTTP errors, timeout handling และทดสอบ GET/POST

การวางสัญญา API เป็นการเพิ่มเอกสารย้อนหลังตามข้อกำหนด; การพัฒนา client/server เกิดใน Sprint 2

## 2. ผลการทดสอบและการทบทวน

เอกสารที่มีไม่ได้แยกจำนวนผลทดสอบของ Sprint 1 ออกจากชุดทดสอบรวม 56 รายการ จึงบันทึกปัญหาที่พบในช่วง Sprint 1 และแนวทางแก้ไขที่ทำต่อใน Sprint 2–3 ไว้เป็นหลักฐานการทบทวนย้อนหลัง

| สถานการณ์ที่พบ | ผลที่คาดหวัง | ผลที่พบก่อนปรับปรุง | แนวทางแก้ไขในงานต่อมา |
|---|---|---|---|
| ป้อนจำนวนแก้วเป็น `0` หลังเลือกตัวเลือกเครื่องดื่ม | ให้กรอกจำนวนใหม่โดยคงตัวเลือกเดิม | กลับไปเริ่มเลือกรายการใหม่ | ปรับให้ถามซ้ำเฉพาะจำนวน |
| ป้อนเงินสดเป็น `inf` หรือ `nan` | ปฏิเสธค่าที่ไม่ใช่จำนวนเงินจริง | ค่าพิเศษผ่านการตรวจหรือทำให้คำนวณผิด | ตรวจค่าด้วย `math.isfinite` |
| ปิดแล้วเปิดโปรแกรมใหม่ | ประวัติขายเดิมยังอยู่ | ประวัติอยู่ใน RAM และหายเมื่อปิด | เพิ่ม JSON persistence ใน Sprint 2 |

## 3. Retrospective: Wow! & Whoops!

**Wow!**
- ได้ต้นแบบ CLI ที่ครอบคลุมเส้นทางขายหลัก ตั้งแต่เลือกเครื่องดื่มจนออกใบเสร็จ
- ฟีเจอร์หลักของร้านกาแฟถูกกำหนดไว้ชัด ทำให้วางขอบเขตการแยกโมดูลใน Sprint ถัดไปได้

**Whoops!**
- การรับอินพุต การคำนวณ และการแสดงผลยังอยู่ใกล้กัน ทำให้ทดสอบและแก้ไขยาก
- ประวัติขายยังไม่ถาวร และการตรวจค่าตัวเลขพิเศษยังไม่ครอบคลุม
- วางแผน refactor เป็น Presentation / Business Logic / Data Access และเพิ่ม JSON storage ใน Sprint 2
